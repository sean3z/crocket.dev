Benchmarks

How crocket holds up
with the production bits left on

I wanted a comparison I could point at with the boring production bits still on: a JSON access log, a request id, a Prometheus histogram, timeouts, and health routes. Here's crocket against Rocket, Axum, Drogon, Fastify, hyper-express, Spring Boot, and FastAPI, on JSON, a single database query, and plaintext

To keep things fair, an addon/module was installed if a given feature was missing; however, all settings are left at their defaults. That rationale, developers are more likely to install an addon if they know something is missing but, tuning configs is usually another burdensome side quest

Further down I also ran a graceful drain, slow clients, oversized posts, connection churn, a ten-minute memory soak, and a contract test

Throughput is one thing. These are the tests I care about when a deploy lands, a client misbehaves, or a body is bigger than you meant to allow

When to scale

Kubernetes usually decides when to add more pods by watching CPU. When a web service is stuck waiting on a slow database instead of crunching numbers, CPU looks almost idle, about 1% here, even while requests pile up and latency doubles, so Kubernetes never scales out. Crocket is the only framework in this benchmark that ships a built-in “how full am I?” gauge, crocket_saturation, out of the box

With a busy pod, CPU pinned at 100% from 4 in-flight requests and crocket_saturation followed, 0.69 at 12 in-flight requests and 0.90 at 16, so an HPA targeting 0.7 adds pods right when requests start to queue. It trails CPU here because it counts 16 busy workers, not 4 cores, so expect it to read low when you run more workers than CPUs. With a slow database, CPU never got past 1.3%, crocket_dependency_saturation hit 1.0 the moment the 16-connection pool filled, and crocket_saturation stayed at 0.00 the whole way. Past 16 in-flight requests, req/s flattened at about 317 and p99 doubled from 52 to 104 ms, and crocket_pod_saturation climbed to 1.0 too, since requests were queueing for workers stuck on the database. crocket_saturation is pod × (1 − dependency), so that pressure cancels out, and the HPA holds instead of adding pods that would only open more connections to the same slow database. No errors in either phase. This ran locally in Docker on crocket's main branch, queued for 0.5.3, with a 4 vCPU limit, 16 workers, and a 16-connection pool. Phase 1 used a test-only route that burns about 15 ms of CPU before a fast query, Phase 2 the regular GET /db with a 50 ms simulated query. None of the other seven frameworks ship a built-in saturation gauge, so they aren't in this one

The production bits people miss

These are the boring ones, and they're the reason this isn't a stripped-down "hello world" comparison. Here's why each one matters, then what was already built in and what I had to add. The wiring notes underneath have the exact packages and settings

  1. Structured JSON logging

    When something breaks at 2 a.m., you want one line per request you can grep, not a pile of unstructured text

  2. Metrics, as a Prometheus histogram

    Averages hide the pain. A histogram tells you if p99 just fell off a cliff

  3. Request timeout

    A stuck handler shouldn't hold a connection forever, or one slow query takes the pod down with it

  4. Request and correlation id

    When a client says it failed, you need a shared id that shows up in their ticket and in your logs

  5. Health and readiness routes

    The load balancer has to know when a pod can take traffic, and when it should stop getting any

  6. Graceful shutdown and drain

    A deploy shouldn't drop the requests already in flight. SIGTERM should finish what's in progress, then exit

  7. Body size limits

    Without a cap, a single oversized post can run a process out of memory

  8. Input and schema validation

    The API should reject a bad body with a clear error, not guess, and not 500

  9. Scaling signal (saturation)

    CPU says almost nothing when a service is waiting on a database. Something has to say how full the pod is, so the autoscaler knows when to add another

How this was measured

Every framework ran on the same DigitalOcean c-4 size. The JSON, query, and plaintext numbers are from NYC1. The crocket and Drogon production tests ran on the same size in SFO2, because c-4 wasn't available in NYC1 that day. The other production tests, and everything for hyper-express, ran back in NYC1. The graceful drain test ran locally in Docker. Crocket's drain and oversized-body rows were re-run locally on main, which is queued for 0.5.3, while every throughput number is still 0.5.2

  • Three droplets. The app, Postgres 16, and wrk2 each got their own 4 vCPU box. DigitalOcean assigns either an Intel Xeon Platinum 8280 or 8358 to that size, and these boxes were 8280s in both regions
  • Load. wrk2 ran -t4 -c128, HTTP/1.1 keep-alive. Every measured throughput run followed a 60 second warmup at 20,000 req/s
  • Max req/s. The median of three 30 second runs at an unreachable rate. That's a throughput number, not a latency one
  • Common rate. Latency is the median of three 30 second runs at a fixed rate: 10,000 req/s for JSON and plaintext, and 4,000 req/s for the single query test. Those figures are coordinated-omission corrected, so a delayed response counts as late. Where a framework couldn't hold that rate, the table shows its latency at a rate it can sustain instead, after a 60 second warmup at that same rate
  • CPU µs/req. The app's user plus system CPU, divided by requests per second, at max. That's the fairer comparison when one framework is a single process
  • Memory and start. Peak RSS is under load, idle RSS is after boot with no traffic, and cold start is container start to the first 200 on /db
  • Load generator. wrk2 had a 4 vCPU droplet, same size as the app. At crocket's max it was only around half busy (JSON about 50%, plaintext about 55%), so I wouldn't call those numbers client-pegged, though a larger generator could still move them
  • Single-process runtimes. Fastify and hyper-express each run as a single Node.js process by default, so they top out around one core. CPU per request is the fairer comparison there
  • Spring Boot histograms. Spring Boot needs a one-line property to expose histogram buckets at /metrics, and it's on for every number here
  • Graceful drain. This one ran locally in Docker, since it doesn't depend on cloud hardware. Every app's /db query hit a Postgres 16 view that sleeps 500 ms, so each request really is in flight inside the server when SIGTERM lands
