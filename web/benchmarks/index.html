Benchmarks

How crocket holds up
with the production bits left on

TechEmpower's Framework Benchmarks were archived in March 2026, and the old result pages aren't up anymore

I wanted a comparison I could point at with the boring production bits still on: a JSON access log, a request id, a Prometheus histogram, timeouts, and health routes. Here's crocket against Rocket, Axum, Drogon, Fastify, Spring Boot, and FastAPI, on JSON, a single database query, and plaintext

Further down I also ran a graceful drain, slow clients, oversized posts, connection churn, a ten-minute memory soak, and a contract test

Production behavior

Throughput is one thing. These are the tests I care about when a deploy lands, a client misbehaves, or a body is bigger than you meant to allow

Graceful drain

I sent SIGTERM while /json traffic was still in flight, then brought the container back up. This is whether a deploy drops the requests already in progress

Load ran for 40 seconds. Stop is SIGTERM to the process exiting. Restart is container start back to a 200
FrameworkOKErrorsStopRestart
crocket41,9403,3871 s4 s
Drogon70,2672,4580 s3 s

During the cut, Drogon had 2,458 errors and crocket had 3,387, and Drogon also got more successful requests through in those 40 seconds. Coming back up, Drogon was ready in about 3 seconds, and crocket took about 4

The production bits people miss

These are the boring ones, and they're the reason this isn't a stripped-down "hello world" comparison. Here's why each one matters, then what was already built in and what I had to add

  1. Structured JSON logging

    When something breaks at 2 a.m., you want one line per request you can grep, not a pile of unstructured text

  2. Metrics, as a Prometheus histogram

    Averages hide the pain. A histogram tells you if p99 just fell off a cliff

  3. Request timeout

    A stuck handler shouldn't hold a connection forever, or one slow query takes the pod down with it

  4. Request and correlation id

    When a client says it failed, you need a shared id that shows up in their ticket and in your logs

  5. Health and readiness routes

    The load balancer has to know when a pod can take traffic, and when it should stop getting any

  6. Graceful shutdown and drain

    A deploy shouldn't drop the requests already in flight. SIGTERM should finish what's in progress, then exit

  7. Body size limits

    Without a cap, a single oversized post can run a process out of memory

  8. Input and schema validation

    The API should reject a bad body with a clear error, not guess, and not 500

A few things to keep in mind

  • The load generator was a 4 vCPU droplet, same size as the app. At crocket's max it was only around half busy (JSON about 50%, plaintext about 55%), so I wouldn't call those numbers client-pegged, though a larger generator could still move them
  • Drogon does beat crocket on the database test, 49,232 req/s against 45,453, and that's real. It also used about 201 MB of RSS under that load, against 32 MB for crocket
  • FastAPI couldn't hold the shared rate on any of the three tests, so a p99 at that rate would just be queueing. The table keeps that flag, and shows latency at a rate it can hold instead, about 60% of its max. It ran four uvicorn workers, one per core
  • Fastify runs as a single Node process, by design, so it tops out around one core. CPU per request is the fairer comparison there
  • Spring Boot needs a one-line property to expose histogram buckets at /metrics. That setting is on for these numbers

How this was measured

Every framework ran on the same DigitalOcean c-4 size. The original JSON, query, and plaintext numbers are from NYC1. When I came back for the drain, soak, and contract tests, that c-4 size wasn't available there, so those ran on the same size in SFO2

  • Three droplets. The app, Postgres 16, and wrk2 each got their own 4 vCPU box. DigitalOcean assigns either an Intel Xeon Platinum 8280 or 8358 to that size, and these boxes were 8280s in both regions
  • Load. wrk2 ran -t4 -c128, HTTP/1.1 keep-alive. Every measured throughput run followed a 60 second warmup at 20,000 req/s
  • Max req/s. The median of three 30 second runs at an unreachable rate. That's a throughput number, not a latency one
  • Common rate. Latency is the median of three 30 second runs at a fixed rate: 10,000 req/s for JSON and plaintext, and 4,000 req/s for the single query test. Those figures are coordinated-omission corrected, so a delayed response counts as late. FastAPI couldn't hold those rates, so the table also shows its latency at a rate it can sustain, after a 60 second warmup at that same rate
  • CPU µs/req. The app's user plus system CPU, divided by requests per second, at max. That's the fairer comparison when one framework is a single process
  • Memory and start. Peak RSS is under load, idle RSS is after boot with no traffic, and cold start is container start to the first 200 on /db
  • Graceful drain. 40 seconds of GET /json, then SIGTERM mid-way, then a restart. Errors during the cut are the ones that didn't drain
  • Slow clients. 16 connections trickled incomplete headers for about 25 seconds, while healthy GET /json traffic kept going
  • Oversized bodies. A 10 MB and a 100 MB POST to /echo
  • Connection churn. The JSON test again, with Connection: close, so every request opens a new connection. Median of three 20 second runs
  • Memory soak. Ten minutes at 3,500 req/s, with RSS sampled every 5 seconds
  • Contract. POST /echo with a valid body, a wrong type, a missing field, an extra field, and malformed JSON. Each framework uses its idiomatic default
