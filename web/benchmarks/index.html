Benchmarks

How crocket holds up
with the production bits left on

TechEmpower's Framework Benchmarks were archived in March 2026, and the old result pages aren't up anymore

I wanted a comparison I could point at with the boring production bits still on: a JSON access log, a request id, a Prometheus histogram, timeouts, and health routes. Here's crocket against Rocket, Axum, Drogon, Fastify, hyper-express, Spring Boot, and FastAPI, on JSON, a single database query, and plaintext

Further down I also ran a graceful drain, slow clients, oversized posts, connection churn, a ten-minute memory soak, and a contract test

Production behavior

Throughput is one thing. These are the tests I care about when a deploy lands, a client misbehaves, or a body is bigger than you meant to allow

Graceful drain

Every count here covers the whole 40 seconds, including the gap while the container came back. Axum and Fastify show the fewest errors, but only because neither app handled SIGTERM, so they kept serving until the container was force-killed 30 seconds later. On Kubernetes that's a pod getting SIGKILLed at the end of its grace period, not a drain. Crocket, Rocket, Drogon, and hyper-express were down in a second or two, Spring Boot took about 9 seconds to come back, and FastAPI dropped the most requests

The production bits people miss

These are the boring ones, and they're the reason this isn't a stripped-down "hello world" comparison. Here's why each one matters, then what was already built in and what I had to add. The wiring notes underneath have the exact packages and settings

  1. Structured JSON logging

    When something breaks at 2 a.m., you want one line per request you can grep, not a pile of unstructured text

  2. Metrics, as a Prometheus histogram

    Averages hide the pain. A histogram tells you if p99 just fell off a cliff

  3. Request timeout

    A stuck handler shouldn't hold a connection forever, or one slow query takes the pod down with it

  4. Request and correlation id

    When a client says it failed, you need a shared id that shows up in their ticket and in your logs

  5. Health and readiness routes

    The load balancer has to know when a pod can take traffic, and when it should stop getting any

  6. Graceful shutdown and drain

    A deploy shouldn't drop the requests already in flight. SIGTERM should finish what's in progress, then exit

  7. Body size limits

    Without a cap, a single oversized post can run a process out of memory

  8. Input and schema validation

    The API should reject a bad body with a clear error, not guess, and not 500

A few things to keep in mind

  • The load generator was a 4 vCPU droplet, same size as the app. At crocket's max it was only around half busy (JSON about 50%, plaintext about 55%), so I wouldn't call those numbers client-pegged, though a larger generator could still move them
  • Drogon does beat crocket on the database test, 49,232 req/s against 45,453, and that's real. It also used about 201 MB of RSS under that load, against 32 MB for crocket
  • FastAPI tops out around 6,000 req/s on these 4 vCPUs, so at the shared 10,000 (or 4,000 for the query test) requests just queue up. Those wouldn't be fair p50 or p99 figures, which is why the table flags them. The latency you see there is from a rate it can hold, about 60% of its max: 3,500 req/s for JSON, 3,600 for plaintext, and 2,400 for the single query. It ran four uvicorn workers, one per core
  • Fastify and hyper-express each run as a single Node process, by design, so they top out around one core. CPU per request is the fairer comparison there. hyper-express also grew to about 480 to 780 MB of RSS at max load, though it settled around 232 MB at 3,500 req/s
  • Spring Boot needs a one-line property to expose histogram buckets at /metrics. That setting is on for these numbers

How this was measured

Every framework ran on the same DigitalOcean c-4 size. The JSON, query, and plaintext numbers are from NYC1. The crocket and Drogon production tests ran on the same size in SFO2, because c-4 wasn't available in NYC1 that day. The other production tests, and everything for hyper-express, ran back in NYC1

  • Three droplets. The app, Postgres 16, and wrk2 each got their own 4 vCPU box. DigitalOcean assigns either an Intel Xeon Platinum 8280 or 8358 to that size, and these boxes were 8280s in both regions
  • Load. wrk2 ran -t4 -c128, HTTP/1.1 keep-alive. Every measured throughput run followed a 60 second warmup at 20,000 req/s
  • Max req/s. The median of three 30 second runs at an unreachable rate. That's a throughput number, not a latency one
  • Common rate. Latency is the median of three 30 second runs at a fixed rate: 10,000 req/s for JSON and plaintext, and 4,000 req/s for the single query test. Those figures are coordinated-omission corrected, so a delayed response counts as late. Where a framework couldn't hold that rate, the table shows its latency at a rate it can sustain instead, after a 60 second warmup at that same rate
  • CPU µs/req. The app's user plus system CPU, divided by requests per second, at max. That's the fairer comparison when one framework is a single process
  • Memory and start. Peak RSS is under load, idle RSS is after boot with no traffic, and cold start is container start to the first 200 on /db
